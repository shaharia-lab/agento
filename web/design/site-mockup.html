Installation

Everything you need to get Agento running, keep it updated, and remove it again.

Requirements

The Claude Code CLI, installed and signed in. Agento runs every agent by launching claude on your machine. If claude works in your terminal, Agento works. There is no Anthropic API key to enter — the app reuses the CLI's own sign-in.

Note

Agento tells you on launch if the CLI is missing, and where it looked. See Troubleshooting → The Claude Code CLI if the banner appears when claude plainly works.

macOS

Open the .dmg and drag Agento to Applications. On first launch macOS may say the app cannot be verified, because these builds are signed but not notarised.

If Gatekeeper blocks the first launch

Right-click the app and choose Open, then confirm. If that does not offer an Open button, clear the quarantine attribute:

# removes the download quarantine flag
xattr -dr com.apple.quarantine /Applications/Agento.app
Careful

Run that only against a bundle you downloaded from the official releases page. It disables the check that would have warned you about a tampered download.

Where your data lives

One directory, one database file, and nothing outside it:

db~/.agento/agento.dbChats, agents, tasks, session cache
key~/.agento/api-signing-key.pk8Per-install keypair, mode 0600
yaml~/.agento/mcps.yamlExternal MCP servers, if you use any

Deleting that directory resets Agento completely. It never touches ~/.claude, which stays Claude Code's.

Finding the Claude CLI where it actually is

A user ran claude --version, got 2.1.231, and Agento told them Claude Code was not installed. They were both right.

Agento does not ship the Claude Code CLI. It spawns it — every agent run is a subprocess, and the CLI's own sign-in is the credential. So the first thing the app does on launch is work out where claude lives, and the first thing it did wrong was assume the answer was on PATH.

A GUI app has a different PATH than your terminal

This is the part that surprises people, and it surprised us. When you launch an application from Finder, the Dock or Spotlight, it inherits launchd's environment, not your shell's. That is /usr/bin:/bin:/usr/sbin:/sbin and nothing else. Every line your .zshrc exported is invisible.

The launch that matters — from the Dock, by a user who has never opened a terminal that day — is exactly the launch where a PATH scan finds nothing.

Worse, there is an install shape that is not on any PATH at all. claude migrate-installer puts the binary in ~/.claude/local and wires it up as a shell alias. No amount of scanning directories will find it, because there is no file to find under any name you would look for.

Five rules, in order

The resolution is now a single function with an explicit order, cached once per launch:

// first hit wins; the answer is cached for the process
1. AGENTO_CLAUDE_EXECUTABLE        // explicit override, trusted
2. claude_executable_path setting   // stored, trusted
3. $SHELL -lic 'command -v claude'  // login shell — finds aliases
4. the process PATH                 // works when launched from a terminal
5. known install locations          // last resort, verified

Rules three through five verify what they find: the path must be an executable file and answer --version with Claude Code's banner, so an unrelated claude on the PATH is skipped rather than spawned on every turn. Rules one and two are taken on trust, because a wrapper script is a documented reason to set them and refusing it would remove the escape hatch.

The bounds are a startup budget, not a ceiling

Both subprocesses run inside the app's setup block, before the window shows. That makes three seconds for the shell probe and two per --version the worst case a user waits for a window — not a generous limit. A pathological shell degrades to "found by a later rule", never to a window that does not open.
