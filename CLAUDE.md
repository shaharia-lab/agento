# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What is Agento

Agento is a local, self-hosted platform for building and running AI agents through a web UI and CLI. It runs on top of the Claude Code CLI already installed on the user's machine (via `github.com/shaharia-lab/claude-agent-sdk-go`) — no separate API key required. It ships as a single Go binary with the React frontend embedded, persisting everything in SQLite at `~/.agento/agento.db`.

Core domain objects:
- **Agents** — user-defined: name, slug, model, system prompt, thinking mode, permission mode, and an explicit tool allowlist (built-in Claude Code tools, local in-process tools, external MCP servers, integrations).
- **Chats** — persistent multi-turn conversations with agents, streamed live over SSE; a tabbed multi-chat workspace runs conversations in parallel.
- **Integrations** — external services (Google, GitHub, Slack, Jira, Confluence, Telegram, WhatsApp) exposed as agent tools, each running as an in-process MCP server.
- **Tasks** — cron-scheduled agent runs with full job history.
- **Triggers** — rules that match incoming Telegram messages and dispatch agent runs, replying on the same channel.
- **Claude Sessions & Insights** — scans local Claude Code JSONL session files for browsing, token/cost analytics, journey timelines, and productivity metrics.

Cross-cutting: OpenTelemetry instrumentation (hot-reloadable from the UI), SMTP notifications, self-update (`agento update`), and an `agento ask` CLI for one-shot queries.

## Commands

### Backend (Go)
```bash
make build          # Build frontend + Go binary (version-injected)
make build-go       # Build Go binary only
make dev-backend    # Run Go backend with dev tag (hot reload not included)
make test           # go test ./...
make bench-scale    # Scale harness against a generated ~/.claude corpus
                    # (SCALE=medium ~800 sessions, SCALE=large 5,000 / 500 projects).
                    # Behind the `scale` build tag, so `make test` never runs it.
make lint           # golangci-lint run ./...
make tidy           # go mod tidy
make generate       # Regenerate all mocks via mockery (reads .mockery.yaml)
```

Run a single Go test:
```bash
go test ./internal/service/... -run TestChatService
```

### Frontend (React/TypeScript)
```bash
cd frontend && npm ci --legacy-peer-deps   # Install dependencies
make dev-frontend            # Vite dev server on :5173
npm run build                # TypeScript check + Vite bundle
npm run lint                 # ESLint
npm run typecheck            # TypeScript strict check (tsc -b — the root tsconfig is a
                             # solution file with "files": [], so plain `tsc --noEmit`
                             # checks nothing and exits 0)
npm run format               # Prettier
npm run test                 # Vitest (run once); test:watch for the watcher
```

### E2E (Playwright)
```bash
cd e2e && npm ci && npm test   # Headless run; npm run test:ui / test:headed / test:debug also available
AGENTO_E2E_PORT=8996 npm test  # …beside a running dev instance, which holds the default port
```
The Claude Sessions specs read the machine's real `~/.claude` corpus and skip
when it is too small to exercise what they check. They exist because two
behaviours cannot be verified through a CDP-driven Chrome tab: it reports
`visibilityState: "hidden"`, which suspends IntersectionObserver delivery and
smooth-scroll animation — so the list's infinite-scroll sentinel and the
transcript's timeline jump both appear not to fire.

### Development Setup
Two terminals are needed in dev mode:
1. `make dev-backend` — Go API server on `:8990` (or `PORT` env)
2. `make dev-frontend` — Vite dev server on `:5173` (proxies API calls to `:8990`)

### Environment
All optional: `ANTHROPIC_API_KEY` (falls back to Claude Code CLI auth), `AGENTO_DATA_DIR` (default `~/.agento`, supports `~` expansion), `PORT` (default `8990`). OpenTelemetry is configured via standard `OTEL_*` env vars or the Settings UI — see `docs/monitoring.md`. Env vars override UI settings; the API returns HTTP 409 (`EnvLockedError`) when a UI update targets an env-locked value.

## Architecture

### Request Flow
```
Browser → Vite (dev) / embedded FS (prod) → React SPA
                                          ↓
                              chi router (internal/server/)
                                          ↓
                              API handlers (internal/api/)
                                          ↓
                              Services (internal/service/)
                                          ↓
                        Storage (internal/storage/) + Agent SDK
```

### Backend Packages

One line per package — list files in a directory to see current contents.

- **`cmd/`** — Cobra commands: `web` (HTTP server), `ask` (CLI), `update` (self-update). Frontend embedding lives at repo root: `assets.go` (`//go:embed frontend/dist`, prod) and `assets_dev.go` (nil FS → server proxies to Vite), wired through `cmd/webfs.go`.
- **`internal/server/`** — Chi router + middleware, wrapped in `otelhttp` for automatic tracing. Mounts `/api`, serves the SPA, exposes a dynamic `/metrics` Prometheus endpoint. Graceful shutdown with 5s timeout.
- **`internal/api/`** — HTTP handlers. `Server` struct holds all service dependencies; `Mount()` registers routes. SSE streaming in `livesessions.go` (per-session mutex serializes concurrent sends). Shared request/response types in `types.go`.
- **`internal/service/`** — Business logic behind interfaces (`ChatService`, `AgentService`, `IntegrationService`, `NotificationService`, `TaskService`, `ClaudeSettingsProfileService`) so handlers never touch storage directly. Typed errors in `errors.go` map to HTTP statuses.
- **`internal/agent/`** — Claude Agent SDK integration: converts agent config to SDK `RunOptions`, executes sessions, streams results; OTel span helpers for per-tool-call and per-run tracing.
- **`internal/storage/`** — SQLite persistence via `modernc.org/sqlite` (pure Go, **no CGo**). One `SQLite*Store` per domain implementing a store interface. `migrate_fs_to_sqlite.go` migrates the legacy filesystem format once. `withStorageSpan` instruments all operations.
- **`internal/config/`** — `AppConfig` from env; shared profile types in `profiles.go` to avoid import cycles.
- **`internal/integrations/`** — Integration registry (Start/Stop/Reload lifecycle). One subpackage per backend (google, github, slack, jira, confluence, telegram, whatsapp), each an in-process MCP server.
- **`internal/trigger/`** — Dispatcher matching incoming Telegram messages against trigger rules, running the matched agent (bounded concurrency), and replying via Telegram.
- **`internal/claudesessions/`** — Scanner/analytics for Claude Code session JSONL files, cached in SQLite. Sub-agent transcripts under `<session-id>/subagents/agent-*.jsonl` (plus their `.meta.json` sidecars) are scanned into `claude_subagent_cache` with their own mtime tracking and rolled up additively: `ClaudeSessionSummary.Usage` stays main-thread, `SubagentUsage` holds delegated work, and `TotalUsage()` is what aggregate reporting uses — with exactly one deliberate exception: **model attribution** (`buildModelBreakdown`) reads `Usage` plus `SubagentUsageByModel` instead (#192), because a sub-agent routinely runs a different model from its parent and crediting delegated tokens to the delegating model made the one chart that should answer "is delegation routing work to cheaper models?" incapable of answering it (18.3% of delegated tokens on the reference corpus were charted under the wrong model). `SubagentUsageByModel` comes from `attachSubagentUsageByModel`, a second grouped read keyed by `(parent_session_id, model)` — the summary select's `LEFT JOIN` groups by session alone, deliberately, so a multi-sub-agent session is not multiplied out, and that collapses the model dimension. Its values sum to `SubagentUsage` exactly; it re-keys tokens, it never changes a total, and when it is absent the builder falls back to the parent's model rather than dropping the tokens. `buildSessionsPerModel` and `MostUsedModel` deliberately keep counting **sessions** under the parent's model, since a session belongs to whoever ran it. Note every event in a sub-agent transcript carries `isSidechain: true`. Cache-creation tokens are split by cache TTL (`usage.cache_creation.ephemeral_5m/1h_input_tokens`) because the tiers bill differently — 1.25× input for 5-minute, 2× for 1-hour — and cost is priced per assistant message against the effective-dated catalog in `internal/pricing/` (never whole-session at the first-seen model), with an explicit "unknown" path so a model with no published rates contributes no cost rather than being priced as another model. Session labels come from Claude Code's own `custom-title` / `ai-title` transcript events (last occurrence wins; neither carries a timestamp) into `native_title` / `ai_title`, resolved as `custom_title || native_title || ai_title || preview` — Agento's own rename lives in `custom_title`, is never written by a scan, and always wins. `message_count` counts conversational turns — user events carrying genuine input plus assistant events containing a text block — while `event_count` holds the raw top-level event total — and since #196 that split holds for **sub-agents too**: `claude_subagent_cache.event_count` stores the value `readSummaryFile` always computed for a delegated transcript and `upsertSubagentRow` used to drop for want of a column. It is deliberately **not** rolled up into the parent's `event_count`, which stays main-thread exactly as `Usage` and `Cost` do; `isUserTurnContent` (`processor.go`) is the single predicate behind all **three** turn-segmentation sites — the scanner's user-turn count, the insight pipeline's `isTurnStart`, and (#227) the journey timeline's `isJourneyTurnStart` — so none of them can drift apart — it rejects two classes: `tool_result` carriers, and **content that opens with one of Claude Code's own injections**, in either shape the harness writes it. #197 covered *string* content (`injectedTurnMarkers`: `<task-notification>`, `<command-message>`, `<command-name>`, `<local-command-caveat>`, `<local-command-stdout>`, `<system-reminder>`); #226 added the *array* shape — content holding **exactly one `text` block** whose text opens with an `injectedArrayTurnMarkers` entry (`[Request interrupted by user]`, `[Request interrupted by user for tool use]` — neither is a prefix of the other, so both are listed) or matches `skillPreamblePattern`, the skill-invocation preamble. Two tables rather than one because the populations do not overlap: the six wrappers only ever appear as strings and these only ever appear as array text. The skill preamble reuses `scanner.go`'s existing regexp rather than a bare prefix, so the colon must be followed by a path token — `Base directory for this skill:` is ordinary prose a person could type. Any other array shape (several blocks, a non-`text` block) is genuine, since the injected forms are always emitted alone. The match is **prefix-anchored after a trim, never a substring**, because a person can legitimately write *about* a marker and the corpus already contains such a prompt. Both lists are **empirical** and will drift as Claude Code adds forms; a missed marker only leaves a count where it already was, so re-sampling is maintenance rather than a correctness dependency. Because the predicate is shared, a change to it moves `message_count`, `turn_count` and the journey's turns alike, plus everything derived from `turn_count` (`StepsPerTurnAvg`, `AutonomyScore`, `TokensPerTurnAvg`, `LongestAutonomousChain`, the response-time averages), so **both** `CurrentScannerVersion` and `CurrentProcessorVersion` must be bumped together — bumping one recreates exactly the drift the shared predicate exists to prevent. The session `preview` deliberately uses a **weaker** rule than the counter: a genuine turn always wins and replaces a wrapper already seeded, but a transcript that never contains one — a slash command and its expansion, ~5% of the local corpus — still takes its preview from the wrapper, because `preview` is the last fallback in `ResolveDisplayTitle` and an empty one renders as a blank, unidentifiable row in the sessions list. The two array-shaped classes — skill-invocation preambles and `[Request interrupted by user]` — used to be counted, for no better reason than that #197's rule read strings only; #226 excluded them (a further ~963 turns on the same 1,598-transcript corpus where #197 removed 1,771), which is why **both** version constants moved again. A wrapper-sourced preview is passed through `fallbackPreviewLabel`, which pulls the command or skill name out of it (`/lab-workflow:github-issue-to-pr`, `skill: github-issue-to-pr`) instead of showing the raw tag soup — so a skill-only session still reads `skill: <name>` now that the preamble takes the *injected* preview path rather than the genuine-turn one. It is still applied on **both** paths, because the marker tables are empirical and a wrapper shape a future release invents reaches the genuine branch until they catch up; unrecognized shapes are left untouched so it still shows something; `isAssistantReply` is the scanner-side other half and has no insight consumer. The sidechain check is deliberately left to each caller, because the flag means "delegated work, skip" in a parent transcript but is set on every event of a sub-agent transcript. Beyond conversation events the scanner reads `pr-link` (linked pull requests, deduplicated by URL into `claude_session_pr`), `system`/`compact_boundary` (compaction count plus dropped tokens — `cumulativeDroppedTokens` is a running total, so the max is the session's figure rather than the sum; older Claude Code releases omit it and those boundaries contribute `preTokens - postTokens` instead), and the `agent-name` / `permission-mode` / `mode` / `relocated` / `worktree-state` metadata events. Those metadata events carry no timestamp and are re-appended on every resume, so last-in-file wins, exactly like the title events. `boundsSessionTimeRange` (`scanner.go`) decides what may extend `start_time`/`last_activity` and is a **denylist on purpose** — an allowlist of "conversation events" would silently shrink the range for sessions ending in a timestamped non-conversation event such as `attachment` or `queue-operation`. `pr-link` is denied despite carrying a real timestamp, because it can post-date the conversation and would reorder the sessions list. Bumping `CurrentScannerVersion` (`scanner.go`) forces a one-time re-read of every transcript on the next scan, for changes that leave cached rows incomplete without any file mtime changing. **Applying a scan's changes is parallel-read, batched-write** (`scan_apply.go`): a pool of `scanReaders()` goroutines (GOMAXPROCS-1, floored at 2 and capped at 8 — this runs on the user's laptop while they work) decodes transcripts, and a single writer commits them `scanBatchSize` at a time. Reading is I/O plus JSON decode; writing is not parallelizable at all, because modernc's SQLite serializes writers — but a transaction per file was 5,000 fsyncs on a full re-read. The triggers for a full re-read are routine rather than exotic (any pricing rate edit, any idle-threshold change), which is why this is the difference between a settings save costing seconds and costing minutes. A batch that fails to commit is logged and dropped rather than retried: the rows carry each file's mtime, so an uncommitted file still looks changed to the next diff. `timeRange.update` normalizes to UTC because the stored bounds are compared **as text** — SQLite holds the driver's `time.Time.String()` rendering, whose lexical order matches chronological order only while every value carries the same zone suffix, and both the list's `ORDER BY` and its keyset predicate depend on that. **Duration means active duration everywhere a user reads one**: sessions are resumable, so the start/last span counts every idle day between sittings — one resumed-after-28-days session carried 82% of the dashboard's "Avg Duration" (476 min shown, 17 min median) — and `IdleGapThreshold()` (`data_settings.go`, 10 minutes by default) is the single definition of "still working": `activeTimeTracker` sums inter-event gaps capped there, sorting timestamps before walking because the pipeline feeds parent-then-sub-agent transcripts whose timestamps interleave — which is also what credits a 40-minute delegated run instead of collapsing the parent's Task wait to one capped gap. The scanner stores it per transcript (`claude_session_cache.active_duration_ms`, `claude_subagent_cache.active_duration_ms`, rolled up by the same LEFT JOIN as usage; `TotalActiveDurationMs()` follows the `Usage`/`SubagentUsage` additive convention, overlap bounded at one capped gap per delegation), the insight pipeline stores its exact merged figure (`session_insights.active_duration_ms`, averaged as `avg_active_duration_ms`), and the journey computes it on read — consumers are the Avg Duration KPI, the sessions list's duration column *and* filter (`sessionMetrics.ts` reads the stored figure, not the timestamps), the "Longest" leaderboard, the expensive-sessions card, and the journey header; the raw span stays stored and shown as secondary context because "first seen → last touched" answers a different question. The same threshold gates the rhythm averages, which **exclude** rather than cap over-threshold gaps — a resume is a new sitting, not a 226-hour reply, and capping would converge every resumed session on the cap; on the Claude side an over-threshold gap is a queued-message artifact (the event carries the typed-at timestamp). `thinking_time_ms` is gone with the heuristics behind it (`turn_duration` system events no longer exist; the 0.5ms/char fallback maxed at 26 seconds over 1,071 sessions): `claude_working_time_ms` (renamed in migration 24) is measured instead, as the subset of active-time gaps that end at an assistant event. **The threshold is user-configurable** from Settings → Data & Analytics, bounded to 1–240 minutes (`config.{Default,Min,Max}IdleGapThresholdMinutes` — defined in `config` because it is the package every layer may import, interpreted only in `claudesessions`), because the right figure depends on how someone works. It lives in `dataSettings`, a process-wide snapshot on the `packagePricing` model: the readers are the scanner, all nine processors, the journey builder and the session list, none of which have a settings dependency and all of which must agree. Since the durations derived from it are **stored** rather than computed on read, changing it invalidates exactly like a rate edit does — `claude_cache_metadata.idle_threshold_ms` records the threshold the cached figures were computed under, and a drift (`idleThresholdStaleness`, `Cache.idleThresholdChanged`) zeroes every cached mtime to force a re-read *and* zeroes `session_insights.processor_version` so the insight worker reprocesses: a user-caused drift cannot be expressed as a version constant, but it makes the same rows stale. Migration 25 defaults that column to 600000 rather than 0 because it is not a guess — the threshold was a compile-time constant until then, so every pre-existing row was necessarily computed under it and a 0 default would make every install re-read its whole corpus to arrive at the numbers it already had. Saving also triggers the scan directly (`Server.applyDataSettings`) rather than waiting for something else to; both paths are idempotent, since the scanner compares the stored value itself and `EnsureScan` admits one scan at a time. **Projects can be excluded from reporting entirely**: `UserSettings.HiddenProjects` (decoded paths, JSON column) is filtered at `Cache.loadOrEmpty` — the single read behind `List`, and therefore behind `GET /api/claude-analytics` and the insights summary — and, since the sessions list stopped loading the corpus, as a `project_path != ?` clause in `buildFilter` (`session_query.go`) as well. Two places rather than one because the paged path never loads the corpus and so cannot inherit the in-memory filter; both read `HiddenProjects()`, which is the single definition. Hidden is not deleted: the transcripts are still scanned and the rows still cached and correct, so unhiding is immediate and costs no re-read. `GET /api/claude-sessions/projects` omits hidden projects so no picker offers one, except for `?include_hidden=true`, which the settings tab needs because it cannot let you unhide a project it is not allowed to show you. **Per-session cost is stored, not derived** (#188): the scan accumulates it per assistant message and persists the four-part breakdown on `claude_session_cache` (and on `claude_subagent_cache`, rolled up by the same `LEFT JOIN` that sums delegated tokens), so `Cost` is main-thread, `SubagentCost` is delegated, and `TotalCost()` is what aggregate reporting uses — exactly mirroring `Usage`/`SubagentUsage`/`TotalUsage()`. The session list, the detail page and the analytics totals all read that one value; nothing re-prices from aggregate tokens, because a summary keeps no per-message timing and could only approximate by picking one model and one instant for the whole session. **Cost is also stored keyed by the model that spent it**: `cost_by_model` (migration 23, a JSON column read and written with its row) is accumulated at the same point each assistant message is priced, because a stored total carries neither the model nor the timestamp of the messages behind it and no later pass could reconstruct it. The delegated half comes from `claude_subagent_cache`'s own per-model rows via the query that already collects delegated usage, so `TotalCostByModel()` credits a sub-agent's spend to the model the sub-agent ran — the rule #192 established for tokens. It re-keys money and never changes it: its values sum to `TotalCost()`, asserted in tests, and `buildCostByModel` sums to `CostSummary`. This is what makes "which model is my money going to" answerable; the token breakdown beside it inverts the answer whenever a non-caching backend is in the mix (89.2% of tokens, 13.7% of cost on the reference corpus). `TotalUsageByModel()` is the token counterpart, used by the insight cards. `UnpricedModels`/`UnpricedTokens` travel with it so a partly-priced total is disclosed as a floor rather than presented as complete — distinct from a non-billable model, which resolves and contributes a confident $0.00. The cost of storing is that a rate edit no longer reaches cached rows on its own: `claude_cache_metadata.pricing_rev` records the catalog fingerprint the costs were computed under, and a drift invalidates every cached mtime to force a re-read, the same mechanism `scanner_version` uses (`pricingStaleness` in `scanner.go`, `Cache.pricingChanged` in `cache.go`). Re-reading is the only correct response, since re-pricing needs each message's own model and timestamp. That re-read is **asynchronous** (#208): `Cache.List` never scans on the request goroutine — it serves the cached rows immediately and calls `EnsureScan`, which admits exactly one background scan under a short critical section rather than holding `c.mu` for the scan's full duration (moving the scan to a goroutine without restructuring the lock would only unblock the *triggering* request). `ensureFresh` is the one place that decides whether a read needs one, so a rate edit or a threshold change reaches the figures whichever surface the user opens. `Cache.List` still waits up to `coldStartScanWait` on a cold cache; **`ListPage` deliberately does not**, because at the target scale the scan behind that wait is minutes and a first-run user would get a timeout and an empty list anyway. `GET /api/claude-sessions/status` therefore carries `files_done`/`files_total` alongside `costs_stale`/`scan_in_progress`, and the list — which already polls it — shows "Scanning ~/.claude… 412 / 1,373 transcripts" instead of "No Claude sessions found". `pricing_rev` is advanced inside the scan only after its changes apply, so a failed scan leaves the drift recorded and retryable. Insight pipeline: 9 processors run in a single pass over the parent transcript followed by each sub-agent transcript; `AttributionProcessor` breaks tool calls down by the skill, plugin, MCP server and sub-agent responsible plus the reasoning-effort tier, counting **per `tool_use` block** because Claude Code splits one assistant message into several events that all carry the same `attribution*` fields, and deriving MCP server/tool from the `mcp__<server>__<tool>` block name because `attributionMcpServer`/`attributionMcpTool` are sticky (they hold the last MCP tool touched and persist onto unrelated later turns). All six breakdowns are aggregated and rendered (#202) — `attributionAgent` was previously decoded and dropped, and `effort_breakdown`/`mcp_tool_breakdown` stored but never surfaced; the MCP-tool panel sits directly under the MCP-server one because it is that chart's drill-down, not a peer dimension. `agent_breakdown` is empty for main-thread-only work, since Claude Code stamps `attributionAgent` on sub-agent transcripts only; `insight_worker.go` reacts to event-bus session events with a 5-minute rescan loop for version-bump reprocessing. `journey.go` builds step-by-step session timelines and nests each delegated sub-agent's steps under the `Task` `tool_use` that spawned it (joined exactly on `toolUseId`), with unmatched sub-agents appended to their turn rather than dropped. Its turn boundaries come from `isJourneyTurnStart` over the shared predicate (#227) — `attachToolResults` only decodes and attaches `tool_result` steps, and no longer doubles as the turn test, so a wrapper no longer opens a turn the session's own `message_count` does not count and a carrier is a carrier whatever position its `tool_result` block sits in. Its one structural departure is deliberate: a transcript that *opens* with a carrier still gets a turn via `ensureTurn`, because those orphan steps need somewhere to live. No version constant covers a journey — it is built on read, never cached. Claude Code no longer emits `progress` events (none across 2.1.177–2.1.224), so the old `progress` rendering path is gone. **Cache hit rate has exactly one definition** (`CacheHitRate`, `cache_hit_rate.go`), the read share of *every* input-side token — fresh input + cache writes + cache reads. Two formulas used to share the name (`cacheRead/(input+cacheRead)` on the dashboard, pinned near 100% and information-free; `cacheRead/(cacheCreation+cacheRead)` in the pipeline, ~74%); the shared denominator is the only one under which a model with no prompt caching scores 0 rather than being excused. Both `buildCacheEfficiency` and `TokenProfileProcessor` call it, so a change there moves stored rows and needs a `CurrentProcessorVersion` bump. **The sessions list is paged and filtered in SQL**, not in the browser: `GET /api/claude-sessions` returns `{items, next_cursor, has_more}`, keyset-paged on `(sort column DESC, session_id DESC)`. Keyset rather than OFFSET so page 50 costs what page 1 does and so a scan completing mid-scroll cannot shift every subsequent page; the tiebreak on `session_id` is what makes the order total, without which two sessions sharing a cost page against each other. `session_query.go` holds the filter builder and — importantly — the SQL definition of every per-session figure the list filters and sorts on, which must match `frontend/src/lib/sessionMetrics.ts` exactly: a row showing $36.30 must not be hidden by "cost at most $40". `internal/claudesessions/testdata/session_metric_vectors.json` is read by both languages' tests so a change to one definition fails the other's. Search is a plain `LIKE` over five columns rather than FTS5, deliberately: scanning short strings over thousands of rows is sub-millisecond, and an FTS index would need a shadow table kept in step with every scanner upsert and delete for no perceptible gain. `GET /api/claude-sessions/facets` answers what a page cannot — the totals across the filtered set, the dropdown options, and the token p90 the bars scale to — as a separate endpoint because the totals change with the filter while the pages change with scrolling. Day grouping stays **client-side**, over the loaded pages, because that is the only arrangement where a day header's roll-up equals the rows beneath it; a server-side `GROUP BY` would report the whole day's totals above however many of its rows had been paged in. `ListProjects` is served from the list the last scan published (`projects.go`) rather than re-walking every project directory per request, with a live walk as the fallback before the first scan. **One window, one set of sessions**: `FilterSessions` (exported from `analytics.go`) is the single definition of what a date range contains — `last_activity` within `[From, To]` inclusive, plus the optional project — and both `GET /api/claude-analytics` and `GET /api/claude-sessions/insights/summary` resolve their parameters through `parseAnalyticsParams` and filter through it. The insights summary passes the resulting IDs to the store, which no longer date-filters at all; that also removed a latent defect, since the DATETIME columns hold Go's `time.Time.String()` rendering (`2024-03-15 12:00:00 +0000 UTC`) and comparing them against an RFC3339 bound compares `' '` with `'T'` at index 10, misplacing every row whose date equals a boundary's. The ID set travels as one JSON parameter expanded by `json_each`, since a placeholder per ID would overflow SQLite's variable limit on exactly the corpora this serves, and an **empty set means empty** rather than everything. Activity charts bucket a session across **every hour between its start and last activity** (`walkSessionHours`), sharing its tokens out by overlap so corpus totals are unchanged: bucketing at `last_activity` made "Activity by Hour of Day" answer *when sessions end*, and span attribution is also what the heatmap's own drill-down has always selected on. Session counts per hour therefore exceed the session total by design, a span beyond two weeks falls back to the end hour, and both are stated in the UI. `buildInsightCards` (`insight_cards.go`) derives the Insights page's actionable cards from stored data plus the pricing snapshot; the cache-savings card is the one figure anywhere that prices a counterfactual and is marked `Estimated` for that reason. **Granularity follows the window**: hourly to 7 days, daily to 120, weekly to 3 years, monthly to 12, yearly beyond — chosen so no series exceeds `maxBuckets`, which is a property of the thresholds rather than a truncation, since a truncated series would be a lie about the window. Every width keys buckets by a `YYYY-MM-DD` (weekly and monthly by their first day), which is the contract `analyticsMetrics.ts` parses, and `bucketStart` is the one definition shared by `bucketKey` and `walkBuckets` — they used to align only by coincidence, so a weekly series would have emitted keys no session could land in. The report carries its `granularity` because a key alone no longer says how wide its bucket is: a per-day average derived from the first and last populated key would stop at the last bucket's *start*. `project_breakdown` folds everything past the top 20 into one `Other projects` row carrying the count it stands for, so the table stays readable and its total stays the window's total. The report is **memoized** (`analytics_cache.go`) in a small LRU keyed by the window plus every input that can change what it answers — `last_scanned_at`, `pricing_rev` and `idle_threshold_ms`, which `claude_cache_metadata` already records for exactly this purpose, plus the hidden-project set, which is process state and so must be fingerprinted. There is no window in which a stale report can be served, because anything that would change one moves the key. The dashboards fire two of these per open (a window and the one before it) and three on Insights, and each used to rebuild from a full corpus load.

- **`internal/eventbus/`** — In-process pub/sub decoupling components (task completion → notifications, session discovered → insight processing).
- **`internal/notification/`** — Event-driven notifications with SMTP email delivery and templates.
- **`internal/pricing/`** — Effective-dated model pricing catalog. Maintained from **Settings → Model Pricing** (#189) over `/api/pricing/catalog` and `/api/pricing/rates`; `service.PricingService` owns the rules, because the store returns untyped errors that would otherwise collapse into 500s. Adding and correcting a rate are deliberately **separate endpoints, not one upsert** — appending leaves history priced at what it was charged, correcting rewrites already-reported costs, so `AddRate` refuses to overwrite (returning the colliding row so the UI can offer to correct instead) and `CorrectRate` refuses to create. `effective_from` is normalized to second precision because that is what RFC3339 storage round-trips; without it a written row is not findable by the value that wrote it. Every mutation invalidates the session cache so #188's stored costs re-price. Internals: `catalog.json` (embedded built-in seed, checked against provider pricing pages), `store.go` (SQLite `model_pricing` CRUD + FNV-1a revision hash; startup re-seed upserts on `(model_pattern, effective_from)` and never clobbers `user_modified` rows), `resolver.go` (exact > prefix matching, then newest `effective_from <= spent_at`; usage predating every row falls back to the earliest marked estimated). Cost is accumulated per assistant message at its own timestamp; consumers read the process-wide snapshot wired by `Cache.WithPricingStore`. The catalog is **not Anthropic-only** — Claude Code is pointed at compatible backends, so Moonshot Kimi, Z.ai GLM and Alibaba Qwen are seeded too. Anthropic's TTL multipliers (5m 1.25×, 1h 2×, read 0.1×) are only the *default* for the cache columns; each is overridable per rate because other providers publish their own cached-input price and do not split cache writes by TTL at all (Alibaba prices caching as a percentage rule — explicit creation 125% of input, hits 10%). Alibaba also **tiers by context length**, which #218 made expressible: a `Rate` carries an ascending `Tiers []TierRate` keyed by an inclusive upper bound on a request's input tokens, persisted in the `model_pricing_tier` child table so `model_pricing`'s `UNIQUE(model_pattern, effective_from)` — and with it AddRate/CorrectRate's collision semantics — is untouched, and an untiered rate simply has zero rows there. `Resolve(model, at)` deliberately keeps its signature; band selection lives in `Rate.Price`, which calls `tierFor` and then the unchanged flat arithmetic (`priceFlat`), so **empty `Tiers` is a nil-slice check and the flat path did not move**. Bands are *selected, not accumulated* — Alibaba bills every token of a request at the chosen band's rate, so there is no progressive-bracket arithmetic — and a request above every declared bound uses the highest band rather than falling back to flat or to zero. The boundary counts **all** input-side tokens (fresh + cache-read + cache-write), encoded once in `Usage.tierInputTokens`: Alibaba states how cached tokens are billed but not whether they count toward the bound, so the reading that they do is documented there and changed only there. `Store.Revision` hashes the bands too, or a band correction would leave `pricing_rev` unchanged and #188's stored costs would never re-price. Seeding upserts bands then prunes undeclared ones (never delete-first — `Seed` has no surrounding transaction, and a crash between would leave a tiered rate silently priced at its base band) and skips `user_modified` rows entirely. The UI renders bands **read-only**; tier editing is deliberately not offered. Because `Price` picks a band *before* applying any price, a user correction that left the bands in place would save and then change nothing at any size — so `UpsertRate` **clears the rate's bands**, making a hand-entered rate flat (user intent over catalog, the same rule `user_modified` encodes elsewhere), and the correct-rate form says so. Two flags disambiguate a $0.00 row: `billable: false` is a deliberate zero (`<synthetic>`, embeddings) that resolves and so never reaches the unknown-pricing bucket, while an unmatched model does; `estimated: true` marks a best-effort rate, used for the bare family aliases (`opus`) that name no concrete model. Non-billable is the only way to seed all-zero rates — elsewhere a zero is an unfilled entry and fails at parse time, so a half-filled row breaks the build instead of quietly under-reporting. A model whose ID is not on a provider's published pricing page is deliberately left out: a missing row is visible in the unknown bucket, a guessed one is not.
- **`internal/logger/`** — Structured `slog`: rotating system log (lumberjack) + per-session logs at `<logDir>/sessions/<id>.log`; `otelslog` bridge forwards logs to OTel when enabled.
- **`internal/telemetry/`** — OTel providers (OTLP gRPC or Prometheus), config persisted to `<data_dir>/monitoring.json`, hot-reload via `Manager.Update()`, pre-built instruments (`agento.http.*`, `agento.agent.*`, `agento.chat.*`, `agento.storage.*`).
- **`internal/updater/`** — Release checker (cached 1h, feeds the UI update banner) and in-place installer behind `agento update`.
- **`internal/daemon/`** — `agento service` backend: installs and manages Agento as a user-level background service (launchd on macOS, systemd user units on Linux), with embedded unit/plist templates and a `commandRunner` seam for tests.
- **`internal/build/`** — Version variables injected via `-ldflags`.

**Timezones**: UTC end to end in storage and transport; **aggregation and display follow the browser** (#190). The analytics and insights endpoints take a `tz` IANA name (the frontend sends `Intl.DateTimeFormat().resolvedOptions().timeZone`), and `AnalyticsParams.Loc` is applied via `.In(loc)` before any bucket key is derived — a day, hour or weekday is meaningless until you say whose it is. A bare `YYYY-MM-DD` `from`/`to` is a **local** day boundary (`time.ParseInLocation`), not a UTC one. Missing or unrecognized `tz` falls back to UTC rather than erroring, so pre-`tz` callers are unchanged. `main.go` imports `_ "time/tzdata"` because a distroless container has no `/usr/share/zoneinfo` and every `LoadLocation` would silently degrade the dashboard to UTC. Daily bucket walks (`walkBuckets`) step the **calendar day**, not 24 hours — a local day is 23 or 25 hours across a DST transition, and a fixed step duplicates one key while skipping another. One deliberate UTC exception on the frontend: `formatRateDate` (`lib/pricing.ts`), because a pricing rate is keyed to a day rather than an instant.

**Import rule**: `config` ← `service` ← `api` (never reverse).

### Frontend

- `frontend/src/lib/api.ts` — typed API client for all backend endpoints.
- `frontend/src/types.ts` — TypeScript types mirroring Go structs; keep in sync when changing API types.
- `frontend/src/App.tsx` — React Router routes; one page component per feature under `frontend/src/pages/`.
- `frontend/src/contexts/` — theme/appearance state.
- Tests are `src/**/*.test.{ts,tsx}`, run under **jsdom** with `src/test/setup.ts` loaded for every suite — it registers `@testing-library/jest-dom`'s matchers and an `afterEach(cleanup)`, so a break there breaks every file at once, not just the one you edited. `@testing-library/dom` is an explicit devDependency rather than an inherited peer, because this repo installs with `--legacy-peer-deps` and would otherwise not resolve it.

### Agent Configuration
Agents are stored in SQLite (legacy YAML files in `~/.agento/agents/` are auto-migrated on first startup); create/edit via UI or API. Permission modes: `bypass` (default), `default`, `plan`, `dontAsk`. System prompts support `{{current_date}}` and `{{current_time}}` template variables.

### MCP Integration
External MCP servers are defined in `mcps.yaml` (or `MCPS_FILE`); local in-process tools go in `internal/tools/registry.go`. Claude settings profiles are stored as `~/.claude/settings_<slug>.json` with metadata in `~/.claude/settings_profiles.json`.
